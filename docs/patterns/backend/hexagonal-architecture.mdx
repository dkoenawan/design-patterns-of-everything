## Summary

Hexagonal Architecture (also called Ports and Adapters) structures an application so that the core domain logic is entirely independent of external systems — databases, APIs, UIs, and messaging infrastructure. External interactions flow through defined ports (interfaces) and are wired up via adapters at runtime.

## Problem

Application logic becomes tightly coupled to infrastructure concerns: database queries embedded in business logic, HTTP transport leaking into domain models, testing requiring live external services.

- How do you test business logic without a real database?
- How do you swap a REST API for a message queue without rewriting the core?
- How do you prevent delivery mechanism concerns from polluting domain code?

## Solution

Define the application core as a set of **ports** — interfaces that describe what the application needs (driven/secondary ports) or what it exposes to callers (driving/primary ports). **Adapters** implement those interfaces and translate between the external world and the application.

```
         [ UI Adapter ]   [ CLI Adapter ]
                  \           /
              [ Primary Port (inbound) ]
                       |
              [ Application Core ]
                       |
              [ Secondary Port (outbound) ]
                  /           \
         [ DB Adapter ]   [ HTTP Adapter ]
```

The core contains use cases and domain logic. It never imports adapters. Adapters import the core and implement or call its ports.

```typescript
// Secondary port — defined by the core, implemented by an adapter
interface OrderRepository {
  save(order: Order): Promise<void>;
  findById(id: string): Promise<Order | null>;
}

// Application core — depends only on the port interface
class PlaceOrderUseCase {
  constructor(private readonly orders: OrderRepository) {}

  async execute(cmd: PlaceOrderCommand): Promise<void> {
    const order = Order.create(cmd.items, cmd.customerId);
    await this.orders.save(order);
  }
}

// Adapter — implements the port, owns the infrastructure detail
class PostgresOrderRepository implements OrderRepository {
  constructor(private readonly db: Pool) {}

  async save(order: Order): Promise<void> {
    await this.db.query(
      `INSERT INTO orders (id, customer_id, items) VALUES ($1, $2, $3)`,
      [order.id, order.customerId, JSON.stringify(order.items)]
    );
  }

  async findById(id: string): Promise<Order | null> {
    const row = await this.db.query(`SELECT * FROM orders WHERE id = $1`, [id]);
    return row ? Order.fromRow(row) : null;
  }
}

// Wiring — swapping to an in-memory adapter for tests requires no core changes
const useCase = new PlaceOrderUseCase(new InMemoryOrderRepository());
```

`PlaceOrderUseCase` never references Postgres. A test suite can inject `InMemoryOrderRepository` and exercise the same domain logic with zero infrastructure.

The same shape holds in Python, using `Protocol` for the port and structural typing for the adapters:

```python
from typing import Protocol, Optional

# Secondary port — defined by the core, implemented by an adapter
class OrderRepository(Protocol):
    async def save(self, order: "Order") -> None: ...
    async def find_by_id(self, order_id: str) -> Optional["Order"]: ...


# Application core — depends only on the port protocol
class PlaceOrderUseCase:
    def __init__(self, orders: OrderRepository) -> None:
        self._orders = orders

    async def execute(self, cmd: "PlaceOrderCommand") -> None:
        order = Order.create(cmd.items, cmd.customer_id)
        await self._orders.save(order)


# Adapter — implements the port, owns the infrastructure detail
class PostgresOrderRepository:
    def __init__(self, pool: "Pool") -> None:
        self._pool = pool

    async def save(self, order: "Order") -> None:
        await self._pool.execute(
            "INSERT INTO orders (id, customer_id, items) VALUES ($1, $2, $3)",
            order.id, order.customer_id, order.items,
        )

    async def find_by_id(self, order_id: str) -> Optional["Order"]:
        row = await self._pool.fetchrow("SELECT * FROM orders WHERE id = $1", order_id)
        return Order.from_row(row) if row else None


# Wiring — swapping to an in-memory adapter for tests requires no core changes
use_case = PlaceOrderUseCase(InMemoryOrderRepository())
```

Because `OrderRepository` is a `Protocol`, `PostgresOrderRepository` and `InMemoryOrderRepository` never need to declare the interface explicitly — the core depends on shape, not inheritance, keeping adapters free to evolve independently.

### Ports speak the domain's language

A port is named for what the core needs, not for how an adapter happens to provide it. `OrderRepository.save(order)` is a port. `OrderStore.executeQuery(sql, params)` only moves the database call behind an interface: the core still writes SQL, and swapping to a document store still means rewriting it.

The same applies to the types in a port's signature. If a port accepts or returns a database row, an ORM entity, a `Pool` or an HTTP `Request`, the core now depends on that technology through the port, and the isolation is lost.

```typescript
// Leaks the adapter: the core must know about rows and SQL errors
interface OrderRepository {
  findById(id: string): Promise<QueryResult<OrderRow>>;
}

// Speaks the domain: the adapter maps rows to Order and errors to domain outcomes
interface OrderRepository {
  findById(id: OrderId): Promise<Order | null>;
}
```

Translation is the adapter's job. It maps rows to domain objects on the way in and domain objects to rows on the way out, and it turns driver errors into something the core can act on, such as `null` for a missing record. Failures the core cannot act on, such as a lost connection, propagate as they are.

### Driving adapters translate, then delegate

On the inbound side, an HTTP controller, a CLI command or a queue consumer is an adapter too. Each one does the same three things: turn the transport input into a command, call the use case through its primary port, and turn the result or domain error back into the transport's terms.

```typescript
// Driving adapter — HTTP in, HTTP out, no business rules
app.post("/orders", async (req, res) => {
  const cmd = PlaceOrderCommand.parse(req.body);   // transport → command
  try {
    const orderId = await placeOrder.execute(cmd);  // primary port
    res.status(201).json({ orderId });
  } catch (err) {
    if (err instanceof OutOfStockError) return res.status(409).json({ error: err.message });
    throw err;
  }
});
```

The use case does not know it was called over HTTP, so a queue consumer for bulk imports can call the same `placeOrder.execute(cmd)` and map `OutOfStockError` to a dead-letter message instead of a 409. If a rule such as "orders over 50 items need approval" ends up in the controller, the queue consumer will skip it. Rules belong in the core, where every driving adapter goes through them.

### Enforce the dependency rule with tooling

"The core never imports adapters" is the rule the whole pattern depends on, and code review alone will not keep it. One `import { pool } from "../adapters/postgres"` added under deadline pressure works, passes its tests, and makes the core depend on Postgres again.

Make the boundary visible in the directory layout and check it in CI:

```
src/
  core/        # domain model, use cases, port interfaces — imports nothing from adapters/
  adapters/    # postgres/, http/, queue/ — import from core/
  main.ts      # composition root — the only file that imports both to wire them
```

In TypeScript, an ESLint `no-restricted-imports` rule scoped to `src/core/**` or a dependency-cruiser rule can fail the build when the core imports from `adapters/` or from infrastructure packages such as `pg` or `express`. In Python, import-linter contracts do the same. A violation then fails the build when it is introduced, instead of being found months later.

### Test every adapter against the same port contract

The in-memory adapter that makes core tests fast can also make them misleading. If `InMemoryOrderRepository.save` accepts two orders with the same id while Postgres rejects the second with a unique-constraint error, the core's tests pass against behaviour production does not have.

Write the port's expected behaviour once, as a contract test suite, and run it against every adapter:

```typescript
function orderRepositoryContract(name: string, make: () => Promise<OrderRepository>) {
  describe(`${name} satisfies OrderRepository`, () => {
    it("returns null for an unknown id", async () => {
      const repo = await make();
      expect(await repo.findById(OrderId.of("missing"))).toBeNull();
    });

    it("returns what was saved", async () => {
      const repo = await make();
      const order = Order.create(["Widget"], "C-1");
      await repo.save(order);
      expect(await repo.findById(order.id)).toEqual(order);
    });
  });
}

orderRepositoryContract("InMemory", async () => new InMemoryOrderRepository());
orderRepositoryContract("Postgres", async () => new PostgresOrderRepository(await testDatabase()));
```

The in-memory run is part of the fast unit suite. The Postgres run belongs to the integration suite against a real database container. When the two disagree, fix the in-memory adapter, so the fast tests stay a faithful stand-in for production.

## When to Use

- Applications with complex business logic that must be unit-tested in isolation
- Systems that need to support multiple delivery mechanisms (REST, GraphQL, CLI, event-driven)
- Projects expecting to swap infrastructure components (e.g., migrating databases)
- Teams enforcing strict separation between domain and technical concerns

**Avoid when:**

- CRUD-heavy applications with minimal domain logic — the abstraction overhead outweighs the benefit
- Small services where the complexity of ports/adapters isn't justified

## Trade-offs

| Benefit | Cost |
|---|---|
| Core logic is fully unit-testable without infrastructure | More boilerplate: interfaces, adapters, wiring |
| Infrastructure is swappable without touching domain code | Indirection can make control flow harder to trace |
| Clear dependency direction enforced by structure | Requires discipline to avoid leaking adapters into core |
| Supports parallel development (core vs. adapters) | Initial setup cost is higher than layered architecture |
