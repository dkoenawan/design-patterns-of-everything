## Summary

Command Query Responsibility Segregation (CQRS) splits an application's data access model into two distinct sides: **commands** that mutate state, and **queries** that read state. Each side is optimized independently — writes enforce business invariants, reads serve UI and reporting needs without those constraints.

## Problem

A single unified data model that handles both reads and writes creates competing pressures that are hard to resolve simultaneously.

- Read operations need denormalized, pre-joined data to serve UIs efficiently — but write models need normalized data to enforce consistency
- Complex domain logic on the write side bleeds into read paths, adding latency and coupling
- Scaling reads and writes together is inefficient when their load profiles differ dramatically
- Adding reporting queries forces compromises in the domain model that reduce its integrity

## Solution

Define two separate models: a **command model** that accepts mutations (create, update, delete) and enforces all domain invariants, and a **query model** (read model) that is optimized for the specific data shapes consumers need.

```
Client
  │
  ├─── Command ──▶ [ Command Handler ] ──▶ [ Write DB / Event Store ]
  │                       │                         │
  │                       │               [ Projection / Sync ]
  │                                                 │
  └─── Query  ──▶ [ Query Handler  ] ◀──  [ Read DB (denormalized) ]
```

**Commands** are intent-carrying messages (`PlaceOrderCommand`, `CancelSubscriptionCommand`). Command handlers validate input, apply domain logic, persist changes, and optionally emit domain events.

**Queries** bypass the domain model entirely — they read directly from a pre-projected read store optimized for the consumer. No business logic runs on the read path.

The two stores can be synchronized synchronously (same transaction, separate tables) or asynchronously (event-driven projections), depending on consistency requirements.

```typescript
// Command side — enforces invariants
class PlaceOrderHandler {
  async handle(cmd: PlaceOrderCommand): Promise<void> {
    const cart = await this.cartRepo.findById(cmd.cartId);
    const order = cart.checkout(cmd.paymentMethod);  // domain logic
    await this.orderRepo.save(order);
    await this.eventBus.publish(order.pullDomainEvents());
  }
}

// Query side — returns exactly what the UI needs
class OrderSummaryQuery {
  async execute(userId: string): Promise<OrderSummaryDTO[]> {
    return this.db.query(
      `SELECT o.id, o.total, o.status, p.name AS product
       FROM order_summaries o JOIN products p ON o.product_id = p.id
       WHERE o.user_id = $1`,
      [userId]
    );
  }
}
```

The same split holds in Python, with the command handler enforcing invariants and the query handler reading straight from a denormalized store:

```python
# Command side — enforces invariants
class PlaceOrderHandler:
    def __init__(self, cart_repo, order_repo, event_bus):
        self._cart_repo = cart_repo
        self._order_repo = order_repo
        self._event_bus = event_bus

    async def handle(self, cmd: PlaceOrderCommand) -> None:
        cart = await self._cart_repo.find_by_id(cmd.cart_id)
        order = cart.checkout(cmd.payment_method)  # domain logic
        await self._order_repo.save(order)
        await self._event_bus.publish(order.pull_domain_events())

# Query side — returns exactly what the UI needs
class OrderSummaryQuery:
    def __init__(self, db):
        self._db = db

    async def execute(self, user_id: str) -> list[OrderSummaryDTO]:
        return await self._db.query(
            """SELECT o.id, o.total, o.status, p.name AS product
               FROM order_summaries o JOIN products p ON o.product_id = p.id
               WHERE o.user_id = $1""",
            [user_id],
        )
```

### Separate models first, separate databases only if needed

CQRS describes a separation of models, not of infrastructure. Each step along the spectrum below adds operational cost, so a system should move along it only when the previous step fails a measured requirement:

| Level | Write side | Read side | Consistency | Move further when |
|---|---|---|---|---|
| 1. Separate code paths | Domain model over normalized tables | Query handlers run hand-written SQL against the same tables | Immediate | Read queries need joins or aggregates that are too slow at request time |
| 2. Separate read tables, same database | Same | Projection tables updated in the same transaction as the write | Immediate | Projection updates make write transactions too slow, or several read shapes compete |
| 3. Separate read store | Same | Search index, document store or cache fed by events | Eventual | — |

Most systems get the main benefit, a domain model free of reporting concerns, at level 1. Level 3 is justified by a different read technology (full-text search, a graph, a key-value cache) or read load that the write database cannot carry. The rest of this section applies once projections are asynchronous.

### Commands acknowledge; queries do not mutate

A command handler returns at most what the caller needs to refer to the change: the new aggregate's id and its version. It does not return a read DTO. Once a command returns the order summary, the write side has to build a read shape, and the two models are coupled again. The reverse rule applies to queries: a query that records "last viewed", increments a counter or lazily creates a missing row is a command, and it will be cached, retried and load-balanced as if it were safe to repeat.

```typescript
type CommandResult = { id: string; version: number };

class PlaceOrderHandler {
  async handle(cmd: PlaceOrderCommand): Promise<CommandResult> {
    const cart = await this.cartRepo.findById(cmd.cartId);
    const order = cart.checkout(cmd.paymentMethod);
    await this.orderRepo.save(order);          // version incremented on save
    return { id: order.id, version: order.version };
  }
}
```

The returned version is what makes read-your-own-writes possible later.

### Publish events with the write, not after it

The handler in the example above saves the order and then publishes its events. Those are two separate systems, so a crash, timeout or broker outage between the two calls commits the order without ever publishing the event. The read model never shows that order, and nothing retries it. Reversing the order is no better: an event can be published for a write that is then rolled back.

The **transactional outbox** removes the dual write. The handler inserts the events into an `outbox` table in the same database transaction as the aggregate, and a separate relay reads the outbox and publishes:

```typescript
await this.db.transaction(async (tx) => {
  await this.orderRepo.save(order, tx);
  await tx.insert('outbox', order.pullDomainEvents().map((e) => ({
    aggregate_id: order.id,
    version: e.version,
    type: e.type,
    payload: JSON.stringify(e),
  })));
});

// Relay (separate process): poll, publish, then mark as sent
const pending = await db.query(
  `SELECT * FROM outbox WHERE sent_at IS NULL ORDER BY id LIMIT 100`
);
for (const row of pending) {
  await broker.publish(row.type, row.payload);
  await db.query(`UPDATE outbox SET sent_at = now() WHERE id = $1`, [row.id]);
}
```

Change-data-capture tools such as Debezium can replace the polling relay by reading the outbox table from the database log. Either way the relay can crash after publishing and before marking the row as sent, so delivery is **at-least-once**. Every consumer must tolerate duplicates, which is the projection's job.

### Projections must be idempotent, ordered and rebuildable

A projection consumes events and updates a read model. Three properties keep it correct under redelivery, reordering and change:

- **Idempotent.** The projection stores the last applied version per aggregate and skips any event at or below it. A redelivered `OrderShipped` then has no effect, instead of shipping the order twice in the read model.
- **Ordered per aggregate.** Events for one aggregate must be applied in version order. Partition the event stream by aggregate id (a Kafka partition key, an SQS FIFO message group). If an event arrives with a version gap, stop and retry rather than applying it out of order.
- **Rebuildable.** A read model is derived data. When its shape changes or a bug corrupts it, build a new table from event history or the write store, switch reads to it, then drop the old one. A read model that cannot be rebuilt has become a second source of truth.

```sql
-- Idempotent upsert: applies only if the event is newer than what is stored
INSERT INTO order_summaries (id, status, total, version)
VALUES ($1, $2, $3, $4)
ON CONFLICT (id) DO UPDATE
  SET status = EXCLUDED.status, total = EXCLUDED.total, version = EXCLUDED.version
  WHERE order_summaries.version < EXCLUDED.version;
```

**Read-your-own-writes.** Once projections are asynchronous, a user who places an order and is redirected to "My orders" may not see it. Do not hide this with a fixed sleep. Use the version returned by the command: the client sends it with the next query, and the query handler waits briefly until the read model has reached that version, or answers from the write side for that one aggregate. For lists, the UI can insert the confirmed item itself and reconcile when the read model catches up. In all cases, measure **projection lag** (now minus the timestamp of the last applied event) and alert when it exceeds the staleness the product has agreed to.

// Commands change the write model and record events in the same
// step. A projector turns those events into read-only summaries
// with the total already computed. Queries only read summaries.

type Item = { name: string; qty: number; price: number };
type OrderEvent =
  | { type: 'OrderPlaced'; orderId: string; version: number; items: Item[] }
  | { type: 'OrderConfirmed'; orderId: string; version: number };
type CommandResult = { id: string; version: number };

// ─── Write side ────────────────────────────────────────────
class OrderWriteModel {
  private orders = new Map<string, { status: string; version: number }>();
  readonly outbox: OrderEvent[] = [];
  private nextId = 1;

  placeOrder(items: Item[]): CommandResult {
    const id = \`ORD-\${this.nextId++}\`;
    // Aggregate and event are stored together: one transaction.
    this.orders.set(id, { status: 'pending', version: 1 });
    this.outbox.push({ type: 'OrderPlaced', orderId: id, version: 1, items });
    return { id, version: 1 }; // an acknowledgement, not a read DTO
  }

  confirmOrder(id: string): CommandResult {
    const order = this.orders.get(id)!;
    if (order.status !== 'pending') throw new Error(\`cannot confirm \${id}\`);
    order.status = 'confirmed';
    order.version += 1;
    this.outbox.push({ type: 'OrderConfirmed', orderId: id, version: order.version });
    return { id, version: order.version };
  }
}

// ─── Read side ─────────────────────────────────────────────
interface OrderSummary {
  readonly id: string;
  readonly status: string;
  readonly total: number;
  readonly itemCount: number;
  readonly version: number;
}

class OrderSummaryProjection {
  private summaries = new Map<string, OrderSummary>();

  apply(event: OrderEvent): void {
    const current = this.summaries.get(event.orderId);
    // Idempotent: a redelivered or older event changes nothing.
    if (current && current.version >= event.version) return;
    const next: OrderSummary =
      event.type === 'OrderPlaced'
        ? {
            id: event.orderId,
            status: 'pending',
            total: event.items.reduce((sum, i) => sum + i.qty * i.price, 0),
            itemCount: event.items.length,
            version: event.version,
          }
        : { ...current!, status: 'confirmed', version: event.version };
    this.summaries.set(event.orderId, Object.freeze(next));
  }

  get(id: string): OrderSummary | undefined {
    return this.summaries.get(id);
  }

  list(): readonly OrderSummary[] {
    return [...this.summaries.values()];
  }
}

// The relay delivers outbox events at least once, from a position.
function relay(write: OrderWriteModel, read: OrderSummaryProjection, from = 0): number {
  write.outbox.slice(from).forEach(e => read.apply(e));
  return write.outbox.length;
}

const write = new OrderWriteModel();
const read = new OrderSummaryProjection();

write.placeOrder([{ name: 'Laptop', qty: 1, price: 900 }, { name: 'Mouse', qty: 2, price: 25 }]);
write.placeOrder([{ name: 'Keyboard', qty: 1, price: 80 }]);
let position = relay(write, read);

console.log('── dashboard renders the order list');

## When to Use

- Systems with high read/write asymmetry — queries vastly outnumber writes, or vice versa
- Complex domains where write logic is difficult to express in a schema that also serves reporting
- Applications that need to support multiple specialized read views of the same data (dashboards, search, feeds)
- Architectures already using domain events — CQRS is a natural fit with Event Sourcing

**Avoid when:**

- Simple CRUD applications — the indirection adds ceremony without benefit
- Teams without experience in eventual consistency — async projection lags can surprise developers
- Small services where a single model is readable and the scalability argument doesn't apply

## Trade-offs

| Benefit | Cost |
|---|---|
| Read and write sides scale independently | Two models to maintain — more code surface area |
| Read model optimized for each consumer | Eventual consistency if projections are async |
| Write side free of reporting concerns | Synchronization logic between stores adds complexity |
| Enables Event Sourcing as a natural extension | Debugging across split stores is harder |
| Clear audit trail when combined with domain events | Higher initial setup cost than a single repository |
| Read models can be rebuilt or reshaped from history without touching the write side | At-least-once event delivery forces an outbox on the write side and idempotent projections on the read side |
