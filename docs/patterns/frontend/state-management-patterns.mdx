## Summary

State management is the discipline of deciding *where* state lives, *who* can change it, and *how* changes propagate through the UI. The central insight is that different state has different scope: local UI state belongs in a component; shared domain state belongs in a store; server state belongs in a cache. Mixing these categories in a single global store creates accidental coupling and makes components hard to reason about in isolation.

## Problem

As applications grow, components need to react to the same data. The naive solution — lifting state to a common ancestor — creates prop drilling: data and callbacks thread through layers of components that neither read nor care about them.

- How do you share state across a component tree without coupling every intermediate component to the shape of that state?
- How do you prevent a single state update from triggering unnecessary re-renders across the entire app?
- How do you differentiate between UI state (is this modal open?), client domain state (selected filters), and server state (the API response) — each with different invalidation and caching requirements?

## Solution

Categorise state by scope and apply the appropriate mechanism to each category.

### Local UI State — `useState` / `useReducer`

State that only one component cares about belongs in that component. Keep it local and co-located.

```tsx
// ✅ Local state — no other component needs to know this modal is open
function FilterPanel() {
  const [isOpen, setIsOpen] = useState(false);

  return (
    <>
      <button onClick={() => setIsOpen(true)}>Filters</button>
      {isOpen && <FilterDialog onClose={() => setIsOpen(false)} />}
    </>
  );
}
```

Use `useReducer` when local transitions are complex or follow a clear command vocabulary:

```tsx
type Action = { type: 'increment' } | { type: 'decrement' } | { type: 'reset' };

function counterReducer(state: number, action: Action): number {
  switch (action.type) {
    case 'increment': return state + 1;
    case 'decrement': return Math.max(0, state - 1);
    case 'reset':     return 0;
  }
}
```

### Shared Client State — Context + Zustand

For state shared across multiple components, choose the mechanism based on update frequency:

**React Context** is appropriate for low-frequency state — theme, locale, current user identity — that rarely changes after mount. Context is a dependency-injection mechanism, not a store: every consumer re-renders whenever the provider's `value` changes identity, and there is no way to subscribe to part of it.

```tsx
const ThemeContext = createContext<'light' | 'dark'>('dark');

export function ThemeProvider({ children }: { children: React.ReactNode }) {
  const [theme] = useState<'light' | 'dark'>('dark');
  return <ThemeContext.Provider value={theme}>{children}</ThemeContext.Provider>;
}
```

A primitive value like `theme` is safe. An object literal is not: `value={{ user, signOut }}` is a new object on every render of the provider, so every consumer re-renders even when nothing it reads has changed. Memoise object values, and when some consumers only *write*, give them a separate context that never changes:

```tsx
const SessionContext  = createContext<Session | null>(null);
const SessionActions  = createContext<SessionCommands | null>(null);

export function SessionProvider({ children }: { children: React.ReactNode }) {
  const [session, setSession] = useState<Session | null>(null);

  // Stable for the provider's lifetime: components that only sign out never re-render
  const actions = useMemo<SessionCommands>(() => ({
    signIn: async (creds) => setSession(await api.signIn(creds)),
    signOut: () => setSession(null),
  }), []);

  return (
    <SessionActions.Provider value={actions}>
      <SessionContext.Provider value={session}>{children}</SessionContext.Provider>
    </SessionActions.Provider>
  );
}
```

**A lightweight store** (Zustand, Jotai, Signals) is appropriate for high-frequency or granular state where you need selective subscriptions — only the components that subscribe to a specific slice re-render.

```tsx
type SortOrder = 'asc' | 'desc';

interface FilterState {
  selectedTags: string[];
  sortOrder: SortOrder;
  addTag: (tag: string) => void;
  removeTag: (tag: string) => void;
  setSortOrder: (order: SortOrder) => void;
}

// Zustand store — fine-grained subscriptions prevent cascade re-renders
const useFilterStore = create<FilterState>()((set) => ({
  selectedTags: [],
  sortOrder: 'asc',
  addTag: (tag) => set((s) =>
    s.selectedTags.includes(tag) ? s : { selectedTags: [...s.selectedTags, tag] },
  ),
  removeTag: (tag) => set((s) => ({
    selectedTags: s.selectedTags.filter((t) => t !== tag),
  })),
  setSortOrder: (order) => set({ sortOrder: order }),
}));

// Only re-renders when selectedTags changes — sortOrder changes are ignored
function TagList() {
  const tags = useFilterStore((s) => s.selectedTags);
  return <ul>{tags.map((t) => <li key={t}>{t}</li>)}</ul>;
}
```

### Server State — Query Caches (TanStack Query / SWR)

API data is not application state. It is a cache of remote truth. Treat it separately: use a query library that handles loading, error, stale-while-revalidate, and background refresh automatically.

```tsx
// ✅ Server state — declarative fetching with automatic caching and invalidation
function PatternList({ domain }: { domain: string }) {
  const { data, isPending, isError, error } = useQuery({
    queryKey: patternKeys.list(domain),
    queryFn: () => fetchPatterns(domain),
    staleTime: 5 * 60 * 1000, // treat as fresh for 5 minutes
  });

  if (isPending) return <LoadingShell />;               // no data yet — not "a request is in flight"
  if (isError)   return <ErrorState error={error} />;    // render the failure; error boundaries catch throws, not props

  return <ul>{data.map((p) => <PatternCard key={p.id} pattern={p} />)}</ul>;
}
```

Branch on `isPending`, not `isLoading`: in TanStack Query v5 `isLoading` is only true while the *first* fetch is running, so a disabled or not-yet-started query is neither loading nor holding data, and `data.map` throws. `staleTime` decides when a cached result is refetched; `gcTime` decides how long an unused one is kept. They are separate knobs, and the default `staleTime` of zero means every new subscriber triggers a background refetch.

Define query keys in one place rather than as inline arrays, because invalidation matches on key prefixes and a typo in one call site silently invalidates nothing:

```ts
export const patternKeys = {
  all:    ['patterns'] as const,
  list:   (domain: string) => [...patternKeys.all, 'list', domain] as const,
  detail: (id: string)     => [...patternKeys.all, 'detail', id] as const,
};
```

### Store the minimum; derive the rest

Most state bugs are two copies of the same fact drifting apart. If a value can be computed from props or other state during render, it is not state — compute it. A `useEffect` that copies one piece of state into another runs *after* the render that used the stale value, costs an extra render, and is the usual source of a list showing filtered results for the previous filter.

```tsx
// ❌ Duplicated state, synchronised by an effect: one render is always stale
const [visible, setVisible] = useState<Pattern[]>([]);
useEffect(() => {
  setVisible(patterns.filter((p) => tags.every((t) => p.tags.includes(t))));
}, [patterns, tags]);

// ✅ Derived during render; memoise only when profiling shows it is expensive
const visible = useMemo(
  () => patterns.filter((p) => tags.every((t) => p.tags.includes(t))),
  [patterns, tags],
);
```

The same rule applies to selections: store the selected *id*, not a copy of the selected object, and look the object up from the current list. A copied object keeps showing the old title after the list refetches; an id either resolves to the current record or to nothing, and both are honest. When a component's local state must reset because its subject changed — an edit form moving to a different record — give it `key={record.id}` so React mounts a fresh instance, rather than resetting fields in an effect.

### Put navigational state in the URL

Filters, sort order, pagination, the active tab and the open detail panel are state the *user* owns: they expect the back button to undo them, a reload to keep them, and a pasted link to reproduce them. That makes the URL their source of truth. Read them from the search params and write them back; do not mirror them into a store, or the two will disagree after the first back-button press.

```tsx
function usePatternFilters() {
  const [params, setParams] = useSearchParams();

  const tags = params.getAll('tag');
  const sort = params.get('sort') === 'desc' ? 'desc' : 'asc'; // parse; never trust the URL's shape

  const toggleTag = (tag: string) =>
    setParams((prev) => {
      const next = new URLSearchParams(prev);
      const current = next.getAll('tag');
      next.delete('tag');
      (current.includes(tag) ? current.filter((t) => t !== tag) : [...current, tag])
        .forEach((t) => next.append('tag', t));
      return next;
    }, { replace: true }); // filter tweaks replace history; page changes may push

  return { tags, sort, toggleTag };
}
```

Because the parsed values feed straight into the query key — `patternKeys.list(domain)` extended with `tags` and `sort` — the URL, the cache entry and the rendered list cannot drift apart. Decide per parameter whether a change pushes a history entry or replaces the current one; pushing on every keystroke in a search box makes the back button useless.

### Subscribe narrowly, and keep snapshots stable

A store only prevents cascading re-renders if each component subscribes to the smallest slice it reads, and if the slice it gets back is referentially stable when nothing changed. Zustand v5 compares selector results with `Object.is`, so a selector that builds a new object or array on every call never compares equal: the component re-renders on every store update, and in v5 it can trigger React's "Maximum update depth exceeded" loop.

```tsx
// ❌ New object every call: re-renders on any store change
const { tags, sort } = useFilterStore((s) => ({ tags: s.selectedTags, sort: s.sortOrder }));

// ✅ One selector per primitive or existing reference…
const sort = useFilterStore((s) => s.sortOrder);

// ✅ …or compare the picked fields shallowly
import { useShallow } from 'zustand/react/shallow';
const { tags, sortOrder } = useFilterStore(
  useShallow((s) => ({ tags: s.selectedTags, sortOrder: s.sortOrder })),
);
```

If you write your own store — or wrap a non-React source such as a WebSocket feed or `matchMedia` — subscribe through `useSyncExternalStore`, not `useState` plus `useEffect`. The effect version subscribes *after* the first render, so an update in between is lost, and under concurrent rendering two components can read different versions of the store in the same commit ("tearing"). `useSyncExternalStore` closes both gaps, with one requirement: `getSnapshot` must return the same reference until the data actually changes, so keep the snapshot immutable and replace it on write rather than returning a fresh object per call.

### Mutate server state through the cache, not around it

Copying fetched data into a client store to edit it is the most common way these categories get mixed: the copy stops receiving refetches, and every later mutation has to update two places. Write through a mutation instead, and either invalidate the affected keys or update the cache optimistically with a rollback.

```tsx
const queryClient = useQueryClient();

const rename = useMutation({
  mutationFn: (input: { id: string; title: string }) => api.renamePattern(input),

  onMutate: async ({ id, title }) => {
    const key = patternKeys.detail(id);
    await queryClient.cancelQueries({ queryKey: key });       // an in-flight refetch must not overwrite the optimistic value
    const previous = queryClient.getQueryData<Pattern>(key);
    queryClient.setQueryData<Pattern>(key, (old) => old && { ...old, title });
    return { previous };
  },
  onError: (_err, { id }, ctx) => {
    if (ctx?.previous) queryClient.setQueryData(patternKeys.detail(id), ctx.previous); // roll back
  },
  onSettled: () => queryClient.invalidateQueries({ queryKey: patternKeys.all }),  // reconcile with the server either way
});
```

Use optimistic updates where the action almost always succeeds and latency is visible — toggles, renames, reordering. Use plain invalidation where the server decides the result (pricing, approval workflows) or where a wrong optimistic value would mislead. Either way, the server remains the source of truth and the cache is the only client copy of it.

### Unidirectional Data Flow

All of these mechanisms share a structural invariant: **data flows down, events flow up**. Components receive state as props or via subscriptions; they emit events (callbacks, store actions) to request changes. They never mutate shared state directly.

```
Store / Context
     │  (state flows down)
     ▼
  Component
     │  (events flow up via actions/callbacks)
     ▼
Store / Context
```

## When to Use

- **Local `useState`**: toggle state, form field values, animation flags — anything no sibling or parent component needs
- **`useReducer`**: multi-field local state with transitions that follow explicit action semantics
- **Context**: auth session, theme, i18n locale — infrequently updated values consumed widely
- **Lightweight store (Zustand/Jotai)**: UI filters, selections, cart contents — shared, frequently mutated client state
- **Query cache (TanStack Query/SWR)**: all data fetched from an API
- **URL search params**: filters, sort, pagination, active tab — anything a user would bookmark, share or expect the back button to undo
- **Derived values**: totals, filtered lists, "is anything selected" — computed during render, never stored

**Avoid when:**

- Reaching for a global store as the default for all state; start local, lift only when you have a concrete sharing requirement
- Putting server-fetched data in a Redux/Zustand store alongside client state — they have different invalidation models and mixing them creates complexity
- Syncing one piece of state into another with `useEffect`; derive it instead
- Passing an unmemoised object literal as a context `value`, or returning a new object from a store selector without a shallow comparison

## Trade-offs

| Benefit | Cost |
|---|---|
| Each state category uses the right primitive | Developers must learn which mechanism to use and when |
| Granular subscriptions limit re-render surface area | Multiple state libraries in one project can be confusing |
| Server state is decoupled from client state, with automatic cache management | Query library setup and tuning (staleTime, gcTime) adds initial overhead |
| Unidirectional flow makes debugging straightforward | Stores and query caches are harder to unit-test than pure local state |
| URL-held state is shareable, reload-safe and back-button aware | URL params are untrusted strings that must be parsed and defaulted, and history push/replace has to be decided per parameter |
| Optimistic cache updates make mutations feel instant | Every optimistic path needs a rollback and a reconciling refetch, or a failed write leaves the UI showing data the server rejected |

// Minimal Zustand-like store: immutable snapshots, replaced on every write

  private state: FilterData = { selectedTags: [], sortOrder: 'asc' };

  subscribe = (cb: () => void) => {
    this.listeners.add(cb);
    return () => { this.listeners.delete(cb); };

  getState = (): FilterData => this.state;

  setState(patch: Partial<FilterData>) {
    this.state = { ...this.state, ...patch }; // new snapshot; untouched slices keep their reference
