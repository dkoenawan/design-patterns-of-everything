## Summary

Micro-Frontend Architecture applies the microservices decomposition model to the UI layer. Instead of a single frontend codebase owned by everyone (and therefore controlled by no one), the product is split into vertical slices — each slice is a self-contained application that a single team builds, tests, and deploys independently. A shell application composes these slices at runtime into the experience a user sees.

## Problem

Frontend codebases suffer from the same coupling problems as monolithic backends — at scale, faster than backends do. Multiple teams committing to a single repository block each other on releases, share a global dependency graph that makes version upgrades catastrophic, and produce a build pipeline that takes 20 minutes for a one-line change in a single team's widget.

- How do you let 10 teams deploy their UI changes without coordinating a shared release train?
- How do you let teams choose the right framework version (or even the right framework) for their bounded context?
- How do you prevent a failure in the recommendations panel from crashing the checkout flow?

## Solution

Divide the product into vertical domains. Each domain owns a remote application — a bundle that exports components or pages. A shell application loads remotes at runtime and places them into named slots in the layout.

### Webpack Module Federation

Module Federation is the most mature runtime composition approach. Remotes expose components; the shell consumes them as if they were local imports.

```javascript
// Remote: recommendations-app/webpack.config.js
new ModuleFederationPlugin({
  name: 'recommendations',
  filename: 'remoteEntry.js',
  exposes: {
    './RecommendationPanel': './src/RecommendationPanel',
  },
  shared: {
    react: { singleton: true, requiredVersion: '^18.2.0' },
    'react-dom': { singleton: true, requiredVersion: '^18.2.0' },
  },
});

// Shell: webpack.config.js
new ModuleFederationPlugin({
  name: 'shell',
  // A static URL is fine for a first spike, but it fixes the remote's
  // location at the shell's build time. Production shells resolve it
  // from a manifest instead (see "Resolve remotes from a manifest").
  remotes: {
    recommendations: 'recommendations@https://cdn.example.com/recommendations/remoteEntry.js',
  },
  shared: {
    react: { singleton: true, requiredVersion: '^18.2.0' },
    'react-dom': { singleton: true, requiredVersion: '^18.2.0' },
  },
});
```

The shell lazy-loads the remote on demand. The error boundary catches both a remote that throws while rendering and a `remoteEntry.js` that fails to download, so either failure degrades one panel rather than the page:

```tsx
// Shell: lazy-loading a remote component with error isolation
const RecommendationPanel = React.lazy(
  () => import('recommendations/RecommendationPanel')
);

function ProductPage({ productId }: { productId: string }) {
  return (
    <main>
      <ProductDetails />
      <ErrorBoundary fallback={<EmptyPanel />}>
        <Suspense fallback={<PanelSkeleton />}>
          <RecommendationPanel productId={productId} />
        </Suspense>
      </ErrorBoundary>
    </main>
  );
}
```

### Cross-Micro-Frontend Communication

Micro-frontends must communicate without tight coupling. Three mechanisms, in order of preference:

**1. URL / routing** — the most durable contract. If a navigation event carries all required state in the URL, remotes need no shared runtime.

**2. Shared event bus** — a lightweight pub/sub on `window` or a singleton module that both shell and remotes import. Event names and payload shapes are the contract, so they live in one typed map that every team imports, and `on` returns an unsubscribe function the remote calls when it unmounts — otherwise each remount adds another listener and the handler fires twice, then three times:

```typescript
// contracts/events.ts: published as a small versioned package
export type BusEvents = {
  'cart:item-added': { sku: string; quantity: number };
  'auth:signed-out': Record<string, never>;
};

// Thin event bus: no direct import between remotes
export const bus = {
  emit<K extends keyof BusEvents>(event: K, payload: BusEvents[K]) {
    window.dispatchEvent(new CustomEvent(event, { detail: payload }));
  },
  on<K extends keyof BusEvents>(event: K, handler: (payload: BusEvents[K]) => void) {
    const listener = (e: Event) => handler((e as CustomEvent<BusEvents[K]>).detail);
    window.addEventListener(event, listener);
    return () => window.removeEventListener(event, listener);
  },
};

// Cart remote emits; checkout remote listens. They never import each other.
bus.emit('cart:item-added', { sku, quantity });

// Checkout remote, inside a component
useEffect(() => bus.on('cart:item-added', refreshSummary), []);
```

Events are not stored. A remote that mounts after an event fired never sees it, so the bus carries notifications ("something changed, re-read it") and never the state itself. A late-loading remote reads current state from the URL, from its own API or from the shared store below.

**3. Shared store module** — a singleton Zustand or Redux store exposed as a shared module. Use only for high-frequency shared state (e.g., auth session, cart count in the header). Treat it as a strict API contract: breaking changes require versioning.

### Cut along business capabilities, not page regions

The decomposition decides whether the pattern pays off. The tempting split follows the screen: a header team, a sidebar team, a main-content team. Every feature then needs a change in two or three remotes, released in order, which brings back the release train the split was meant to remove. Split vertically instead. A team owns a business capability (search, product detail, checkout, account) from its routes and UI down to the backend-for-frontend it calls, and a typical change lands in one remote.

Two composition levels follow from that:

- **Route-level composition** is the default. The shell maps a URL prefix to a remote (`/checkout/*` → checkout) and hands over the whole page. The remote owns everything below its prefix, including its internal routes, and nothing else renders inside it. Most remotes should only ever be composed this way.
- **Fragment-level composition** is for the few capabilities that appear on other teams' pages, such as a recommendations strip on product detail or a mini-cart in the header. A fragment takes a narrow, typed props contract (`productId`, never the host page's state object) and must render something useful on its own if the host passes nothing optional.

A useful test of the boundaries: trace the five most common user journeys and count how many remotes each one touches and how many events cross between them. A journey that ping-pongs events between two remotes on every interaction is one capability split in two, and those remotes should merge. One team can own several remotes. One remote should never have two owning teams.

### Treat shared dependencies as a versioned contract

Module Federation's `shared` setting decides what the shell and remotes load once and what each brings in its own copy. React has to be a singleton, because two copies on one page give two hook dispatchers and the first hook in a remote fails with "Invalid hook call". But `singleton: true` alone is lenient. When a remote declares `requiredVersion: '^19.0.0'` and the share scope already holds React 18, webpack logs a console warning and the remote runs against React 18 anyway, so the failure appears later as a missing API in production. Adding `strictVersion: true` turns the mismatch into a rejected import, which the shell's error boundary catches at load time:

```javascript
shared: {
  react: { singleton: true, strictVersion: true, requiredVersion: '^18.2.0' },
  'react-dom': { singleton: true, strictVersion: true, requiredVersion: '^18.2.0' },
  '@acme/design-tokens': { singleton: true, requiredVersion: '^3.0.0' },
  '@acme/contracts': { singleton: true, requiredVersion: '^2.0.0' },
},
```

Keep the shared list short: the framework runtime, the design-system tokens and primitives, and the contracts package holding the bus event map and fragment prop types. Each shared library is a dependency every team must upgrade together, so every entry gives back some of the independence that motivated the split. Lodash or a date library does not belong there; let each remote bundle its own.

The singleton framework also limits the "different framework per remote" benefit. A remote that really runs a different framework, or a different major version, cannot share React components with the shell. It exposes a framework-neutral lifecycle instead, and the shell treats it as a black box:

```typescript
// contracts/mount.ts: the only interface a non-React remote exposes
export interface MountableRemote<P> {
  mount(el: HTMLElement, props: P): { update(props: P): void; unmount(): void };
}
```

Wrapping that lifecycle in a Web Component (`<acme-recommendations product-id="sku-42">`) gives the same contract to any host. Framework upgrades then happen one remote at a time, because each remote bundles its own runtime, at the cost of shipping that runtime twice during the migration.

### Resolve remotes from a manifest, and cache by content

Independent deployment depends on how `remoteEntry.js` is cached. The entry file is a small loader that names the remote's content-hashed chunks. If the CDN serves it with a long `max-age`, users keep loading last week's remote for days after a deploy. If the chunks are not content-hashed, a new entry file can load old chunks from a browser cache, and the two halves of one remote disagree. The rule that works:

| Asset | URL | Cache-Control |
|---|---|---|
| Manifest (`/mf-manifest.json`) | stable | `no-cache` (revalidate on every boot) |
| `remoteEntry.js` | versioned path, e.g. `/recommendations/4.12.0/remoteEntry.js` | `public, max-age=31536000, immutable` |
| Chunks | content-hashed file names | `public, max-age=31536000, immutable` |

Only the manifest is mutable. A deploy uploads a new versioned directory, which changes nothing for users yet, and then rewrites one line in the manifest. A rollback rewrites the line back, so it takes seconds and needs no rebuild of the shell or the remote. The manifest is also where canary releases go: the shell can choose the entry URL per user from a flag. The shell loads remotes from it with webpack's runtime container API instead of the static `remotes` map:

```typescript
declare const __webpack_init_sharing__: (scope: string) => Promise<void>;
declare const __webpack_share_scopes__: { default: unknown };

type Container = {
  init(scope: unknown): Promise<void>;
  get(module: string): Promise<() => any>;
};

const containers = new Map<string, Promise<Container>>();

function loadContainer(scope: string, url: string): Promise<Container> {
  // Memoised: init() must run once per container, and concurrent
  // slots asking for the same remote must share one script tag.
  if (!containers.has(scope)) {
    containers.set(scope, new Promise((resolve, reject) => {
      const script = document.createElement('script');
      script.src = url;
      script.onerror = () => {
        containers.delete(scope); // allow a retry on next navigation
        reject(new Error(`remote ${scope} failed to load from ${url}`));
      };
      script.onload = async () => {
        try {
          await __webpack_init_sharing__('default');
          const container = (window as any)[scope] as Container;
          await container.init(__webpack_share_scopes__.default);
          resolve(container);
        } catch (err) {
          reject(err);
        }
      };
      document.head.appendChild(script);
    }));
  }
  return containers.get(scope)!;
}

export async function loadRemoteModule(scope: string, module: string) {
  const manifest = await fetch('/mf-manifest.json', { cache: 'no-cache' }).then((r) => r.json());
  const container = await loadContainer(scope, manifest[scope]);
  const factory = await container.get(module);
  return factory();
}

// Shell usage. A rejected promise surfaces in the slot's error boundary.
const RecommendationPanel = React.lazy(() =>
  loadRemoteModule('recommendations', './RecommendationPanel'),
);
```

Runtime resolution adds a request waterfall (manifest, entry file, chunks), and it falls on the critical path. Fetch the manifest once at boot, then add `<link rel="preload" as="script">` for the entry files of the remotes the current route will need, so they download in parallel with the shell's own bundle. Give each remote a performance budget in its own CI, because no single team sees the total page weight.

### Isolate styles and globals, share tokens

Remotes run in one document, so anything global becomes a shared, unowned dependency between teams. Three kinds of leak cause most incidents:

- **CSS.** Global selectors from one remote (`.button`, `h2`, a reset stylesheet) restyle every other remote on the page, and whichever stylesheet loads last wins, so the result changes with network timing. Scope every remote's styles with CSS Modules or a build-time prefix (`.reco-…`), and never ship a reset from a remote; only the shell owns base styles. Web-Component remotes get stronger isolation from Shadow DOM.
- **Design tokens.** Share appearance through CSS custom properties that the shell defines on `:root` (`--color-surface`, `--space-3`), not through shared class names. Custom properties are inherited into shadow roots, so one token set themes isolated and non-isolated remotes alike, and a rebrand is one shell change.
- **Runtime globals.** Only one router can own `history`. The shell owns it, and each remote receives its base path and a `navigate` function through props or the mount contract. It never creates its own browser router. Polyfills, `window` patches, global error handlers and analytics initialisation also belong to the shell, which injects them. A remote that patches `fetch` for its own logging has patched it for everyone else as well.

A lint rule per remote (no element selectors or `:global` outside the shell, no `window.history` or `createBrowserRouter` imports) catches most of these leaks before they reach integration.

### Deployment Contract

Each remote publishes a `remoteEntry.js` at a stable URL. The shell resolves remote URLs at runtime (from config or a manifest API), not at build time. This is what enables independent deployment: the shell does not need to be rebuilt when a remote changes.

```
┌─────────────────────────────────────────┐
│              Shell Application          │
│  ┌──────────┐  ┌──────────┐  ┌───────┐ │
│  │  Header  │  │  Sidebar │  │ Slots │ │  ← Shell owns layout
│  └──────────┘  └──────────┘  └───┬───┘ │
│                                  │     │
└──────────────────────────────────┼─────┘
                                   │ runtime load
        ┌──────────────────────────┼──────────────────┐
        │                          │                  │
   ┌────▼────┐               ┌─────▼──────┐   ┌──────▼─────┐
   │ Product │               │  Reviews   │   │   Cart     │
   │  Team   │               │   Team     │   │   Team     │
   │ Remote  │               │   Remote   │   │   Remote   │
   └─────────┘               └────────────┘   └────────────┘
   (deploys independently)   (deploys independently)
```

## When to Use

- Multiple product teams contributing to a single user-facing application where release coordination is a bottleneck
- A product with clearly bounded vertical domains (search, checkout, recommendations, account) that map cleanly to team ownership
- A long-running migration from a legacy monolith: the shell wraps the old app while new remotes are extracted incrementally
- Different domains with legitimately different performance or framework requirements (e.g., a data-heavy dashboard team wanting Svelte while the shell runs React)

**Avoid when:**

- A small team owns the entire frontend — the deployment isolation benefit does not justify the operational overhead of maintaining a shell + multiple remotes
- Domain boundaries are unclear; premature decomposition creates chatty cross-remote dependencies that are worse than a monolith
- Shared UI state between remotes is frequent and complex — tight data coupling between remotes signals the decomposition is wrong

## Trade-offs

| Benefit | Cost |
|---|---|
| Teams deploy independently; no shared release train | Distributed system complexity: remote availability, version skew, CDN cache management |
| Failure in one remote is isolated by an error boundary | Duplicate framework bundles inflate initial load unless shared modules are carefully configured |
| Teams can adopt different frameworks or versions per domain | Testing the integrated product requires a full composition environment |
| Legacy monolith can be extracted incrementally | Cross-remote debugging is harder: stack traces cross bundle boundaries |
| Scales team autonomy without scaling coordination overhead | Shared state contracts between remotes must be versioned as APIs |
| Rollback is a one-line manifest change, with no rebuild | The manifest, entry-file caching and preload hints become infrastructure someone must own |
| Strict shared versions turn skew into a caught load error | Every shared library is an upgrade all teams must take together |
